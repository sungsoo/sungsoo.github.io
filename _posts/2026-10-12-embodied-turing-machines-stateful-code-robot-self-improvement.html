PART 01

문제를 다시 정의하기

로봇의 지능을 어디에 둘 것인가

로봇이 물체를 집고 옮기는 동안 매번 거대 모델을 호출해야 하는가? 이 논문은 지능의 위치를 실행 중 추론에서 측정 가능한 상태, 재사용 코드, 오프라인 개선 절차로 옮긴다. 물체 위치와 로봇 상태를 충분히 정확히 표현하고 실패 대응을 코드로 작성할 수 있다면, 같은 작업의 새로운 배치에서도 고정된 프로그램이 행동할 수 있다는 가설이다.

논문 보고 · Kairui Hu, Siyuan Hu, Fangzhou Hong, Zhaoxi Chen, Ziwei Liu가 제시한 기술보고서이며, 소속은 Nanyang Technological University와 Ropedia다. 첨부는 arXiv:2610.12369v1, 2026-10-08 버전이다. 본 해설의 게시일은 2026-10-12 KST이며, 논문 발표일과 구분한다. 실험 결과를 독립 재현한 글은 아니다.

추상적 튜링 기계의 테이프를 로봇과 환경의 상태에 대응시키고, 읽기를 지각, 쓰기를 행동, 전이 규칙을 정책 코드에 대응시킨다. 작업의 진행 단계·기억·재시도 횟수는 기계의 내부 제어 상태에 해당한다. 이는 설계 관점의 추상화다. 물리 세계 전체를 완벽히 계산할 수 있음을 증명한 정리로 읽어서는 안 된다.

COAP의 핵심은 상태와 결정 규칙을 함께 명시하고, 온라인에서는 고정된 코드를 실행하며 오프라인에서 그 코드를 개선하는 것이다. “모델 없는 실행”은 개발 단계에서 모델을 전혀 쓰지 않았다는 뜻이 아니다. 저자들은 Claude Opus 5.5 계열 코딩 에이전트가 코드 작성·평가·디버깅을 수행했다고 보고한다.

기존 방법과 구분되는 두 축

VLA는 관찰에서 행동으로 가는 매핑을 학습 가중치에 담는다. Agent-as-Policy와 Harness VLA는 추론·도구·기억을 조직하지만 실행 중 모델이 결정을 내린다. 기존 Code-as-Policy도 프로그램을 사용하므로, 단순히 “코드를 사용한다”는 것만으로 COAP의 차이가 설명되지 않는다.

계열 프로그램 생성 시점 상태의 주요 원천 이 논문이 강조하는 차이
Code as Policies, ProgPrompt, VoxPoser 및 후속 계열 실행 중 생성·재계획 가능 지각 API·학습 모델 모델 호출과 외부 지각 불확실성 유지
PyRUA-Lean, Skill2Real 셀 또는 의사결정 단계별 생성·구성 SAM 등 학습 지각 에피소드별 모델 개입
RHO, EmbodiedSWE 오프라인 프로그램 학습 지각 또는 시뮬레이터 oracle 프로그램 밖에서 상태를 공급
COAP 오프라인 작성·검증 후 고정 RGB·고유감각을 처리하는 측정 코드 상태 측정과 정책 규칙을 함께 개선

관련 연구는 ReAct·Toolformer의 도구 사용, SayCan·Inner Monologue의 피드백 기반 계획, CodeAct·Voyager·SWE-agent의 코드 인터페이스, RoboRSI의 무회귀 게이트를 연결한다. 비교 벤치마크로 LIBERO, RoboTwin 2.0, RoboCasa365, RoboDojo를 논의한다. 이러한 비교는 논문 저자의 정리이며 모든 VLA나 모든 에이전트 구현에 대한 보편적 판정은 아니다.

PART 02

명시적 상태와 다섯 수식

세 부분의 상태, 다섯 범주의 기록

RoboDojo 관찰에는 지시문, 머리 카메라와 양 손목 카메라의 RGB 영상, 관절각, 말단 자세, 그리퍼 명령 echo가 포함된다. COAP은 이를 환경 상태·로봇 상태·작업 상태로 조직한다. 논의에서는 로봇, 물체, 환경, 관계, 작업이라는 다섯 범주로 더 세분한다.

상태 기록 내용 갱신·유지 방식
로봇 관절각, 말단 자세, 그리퍼 개방, 손에 든 물체, 도달 가능 자세 고유감각을 매 단계 반영
물체·환경 위치, yaw, 크기, 범주, 테이블 및 환경 좌표 측정 코드와 카메라 영상
관계 물체 위·아래, 손에 들림, 지지·배치 관계 행동 결과와 측정 기록
작업 단계, 물체별 담당 팔, 재시도 횟수, 숨겨진 색상 등 기억 작업 프로그램이 갱신
측정 메타데이터 오차, 출처, 시간, 신뢰도·유효성 오래된 측정과 현재 근거를 구분

환경·로봇 상태는 테이프이고, 작업 상태는 내부 제어 상태다. 상태를 하나의 문자열 메모리로 취급하지 않고 물리 단위와 관계를 가진 자료구조로 유지한다. 다음 행동은 한 번의 모터 명령이 아니라 다음 궤적 구간일 수 있다.

(xt+1,at)=Fθ(xt,ot)(1)

식 (1)에서 θ는 소스 코드, xₜ는 명시적 상태, oₜ는 관찰, aₜ는 다음 궤적 구간이다. 실행 동안 θ는 고정되고 xₜ만 바뀐다. 새로운 에피소드의 배치는 새로운 상태로 처리한다. 다만 센서 오차나 물리계의 비결정성까지 사라지는 것은 아니다.

RGB에서 측정값을 만드는 과정

NumPy·OpenCV 기반 지각 코드는 관절각으로 로봇 메시를 영상에 투영해 로봇 픽셀을 제거한다. 테이블 색과 다른 연결 영역을 후보로 찾고, 테이블에 닿는 경계 픽셀의 광선을 테이블 평면과 교차시킨다.

p=c+λd,λ=z0−czdz(2)

c는 카메라 중심, d는 광선 방향, z₀는 테이블 높이다. λ를 구하면 경계 픽셀의 평면상 위치 p를 얻는다. 이후 알려진 3D 형상을 후보 근처에 배치하고 위치·yaw를 탐색해 관측 영역과의 겹침이 가장 큰 정합을 선택한다. 카메라 모델, 로봇 메시, 물체 형상과 테이블 높이는 벤치마크가 제공하는 고정 자산이다.

WorldState는 가림 뒤에도 마지막 측정 자세를 보존한다. 밀리미터 정밀도가 필요한 작업은 마지막 접근 전에 손목 카메라로 다시 측정한다. 식 (2)는 알려진 평면과 형상에 의존하는 기하 추정이며, 임의 환경의 일반적인 3D 복원 해법은 아니다.

라이브러리 확장의 호환성과 개선 게이트

작업 프로그램 → 물체군 모듈 → 조작 모듈 → 지각·운동 모듈의 하향 의존 구조를 사용한다. transfer 호출은 파지 후보 생성, IK·충돌 검사, 재측정, 접근·그리퍼 폐쇄, 짧은 들어올림·보유 확인, 운반·배치·해제, 최종 검증으로 전개된다. 각 단계는 측정 근거와 결과를 반환한다.

확장 방식은 기존 모듈의 조합, 작업 상속과 한 결정의 override, 기본값이 기존 행동을 보존하는 새 선택 매개변수다. 예를 들어 lift_dir의 기본값은 수직 들어올림을 유지하고 특정 작업만 대각선 들어올림을 요청한다.

Bi(θ+δ,o)=Bi(θ,o)∀o∈Otest(3)

Bᵢ는 작업 i의 실행 흔적, δ는 코드 확장, O_test는 단위시험 fixture 집합이다. 식 (3)의 호환성 조건은 새 매개변수를 쓰지 않는 작업과 시험 관찰 범위에 적용된다. 모든 가능한 물리 환경에서 동등함을 입증한 것은 아니다.

Ck={θk+Δk,1,…,θk+Δk,m}(4)

식 (4)는 승인 코드 θₖ에 후보 diff Δₖ,ⱼ를 더한 실행 가능한 분기 집합이다. 각 에이전트는 별도 git worktree에서 실패 기록을 읽고 변수나 규칙을 수정한다. 수치 장면에서 단계 목표 도달 여부를 확인하고, 로봇·물체 메시로 각 waypoint의 IK 해와 충돌을 검사한 다음 검증 에피소드를 실행한다.

Jq(θk+Δ;Vq)≥Jq(θk;Vq)+εq(5)

J_q는 작업 q의 검증 배치 V_q에서 성공한 에피소드 수이며, ε_q는 재실행 잡음을 넘는 개선 여유다. 식 (5)를 만족하는 후보만 다음 기반 코드로 채택하고, 나머지는 합치지 않는다. 디버깅용 development set과 선택용 validation split은 구분되며 최종 test layout은 개발에 사용하지 않았다고 보고한다. 개발 중에는 측정 오차를 분석하기 위해 simulator ground truth를 비교할 수 있지만, 시험 실행에서 oracle 상태를 입력으로 사용하는 것은 금지한다.

PART 04

상태·실행·확장성의 세 장점

A. Explicit State: inspectable, persistent, accurate

상태와 규칙이 변수·자료구조·함수로 드러나면 실패를 특정 측정이나 결정으로 추적하기 쉽다. cover_blocks에서는 처음 측정한 블록 색상과 위치를 저장하고 동일한 컵으로 가린 뒤에도 요구 색 순서대로 컵을 치운다. COAP의 Memory 89.9%는 논문 그림에서 약 90%로 반올림되어 제시된다.

정확성 분석에서 같은 프로그램이 measured state에서는 63%, oracle state에서는 83% 성공한다. 이는 특정 분석의 비교값이며 전체 42작업 평균과 혼합해서는 안 된다. 정밀 측정은 성능 상한의 병목이지만 oracle을 실서비스에 투입할 수 있다는 뜻도 아니다.

B. Execution: controllable, recoverable, efficient

테두리 파지로 잡은 그릇이 운반 중 미끄러지면 운반 속도를 낮추는 코드 수정으로 대응할 수 있다. 파지 후 물체가 들어올림을 따라오지 않는 경우, 마지막 확인 상태로 돌아가 재측정하고 새로운 파지 각도로 다시 시도한다. 이는 단순 반복 호출과 다른 근거 기반 복구다.

문제가 생긴 에피소드 중 프로그램이 문제를 알아차린 비율은 약 76%, 새 방법으로 재시도한 비율은 34%다. 재시도 자체가 항상 성공한 것은 아니다. 세부 결과는 다음 부록 표에 있다.

호출 중앙값은 CPU에서 0.3 ms, 에피소드당 결정 중앙값은 352회다. 다수 호출은 이미 계획된 행동을 전달하며 약 25회의 지각·계획 호출이 결정 시간의 99.4%를 차지한다. 그러므로 0.3 ms를 모든 지각·계획 단계의 비용이나 실제 로봇의 전체 제어 지연으로 읽지 않는다.

VLA 대비 0.8–2.4%, Agent Harness 대비 0.1% 미만의 계산량은 논문 추정이다. CPU 1코어의 10¹¹ FLOP/s 최고 성능을 COAP의 상한으로 사용하고, 3B action-chunk VLA·7B 매-step VLA·2×10¹¹ active-parameter harness에 가정된 호출량을 대입한다. 실측 wall-clock·전력·총개발비를 동일 조건에서 비교한 수치가 아니다.

C. Extensibility: reusable, fast to evolve, cumulative

새 작업이 실행하는 코드의 약 83%가 라이브러리에서 온다. 파지를 물체별로 다시 작성하기보다 top·side·handle·rim·edge·cloth pinch 같은 접촉 방식으로 추상화한다. 기존 작업의 흐름을 상속하고 배치 규칙만 바꾸거나, 기본값이 보존되는 매개변수를 추가한다.

논문은 새로운 작업 개발에서 약 15시간 내 평균 성공률 47%를 보고한다. 그러나 비교 VLA·Agent Harness 개발 곡선과 “지수적 누적 성장” 곡선 일부는 schematic이다. 계측된 장기 지수 성장 법칙이나 동일 자원 하의 완전한 온라인 학습 비교로 주장하지 않는다. OpenVLA의 작업별 5–15시간·8 A100 fine-tuning 비용과 π0.5의 순차 학습 86.9→31.4 사례는 다른 선행 연구의 보고값이다.

PART 05

RSI를 검증 가능한 코드 탐색으로

보이는 실패, 통제된 변경, 누적 개선, 빠른 진화

이 논문이 사용하는 RSI는 실패 확인 → 정책 코드 변경 → 개선 시 채택을 반복하는 과정이다. 모델의 가중치나 학습 알고리즘이 자율적으로 무제한 재설계되는 일반적 RSI와 구분해야 한다. 코딩 모델의 능력, 상태 표현, 라이브러리 추상화, 검증 데이터와 계산 예산이 이 반복의 범위를 정한다.

예를 들어 머그 파지를 테두리·손잡이·몸체·위쪽 접근 등 8개 대안으로 나누어 동시에 평가한다. 하나의 결정에 대한 분기들이 완전한 프로그램이므로 같은 배치에서 비교한 뒤 다음 결정으로 넘어갈 수 있다. 논문은 이를 BFS 형태로 설명한다. 후속 운반·매달기 분기 일부는 도식적 예시다.

36개 분기에서 성능 하락 36%, 변화 없음 11%, 작은 개선 36%, 채택 17%가 보고된다. 30개 에피소드 중 부모보다 최소 4개 더 성공해야 채택하는 예시다. 재실행 변동은 1–3개 에피소드라고 보고한다.

분기 수를 늘린 곡선은 효과를 복원추출하고 최고 후보를 고르는 bootstrap 추정이며 5·95 percentile band를 사용한다. 분기 독립성을 가정하고 작업 간 효과를 모으므로, 선택에 쓰인 배치의 개선을 실제 일반화 개선으로 그대로 읽으면 낙관적일 수 있다. 가장 분주한 개발 구간에는 12개 작업 평가를 병렬 수행해 순차 실행 시간의 17%에 완료했다는 기록도 있다. 이는 전체 프로젝트의 상시 속도 향상 비율이 아니다.

library freeze 뒤 병합에서 전체 SR은 66.5%에서 70.24%로 상승했다고 보고한다. 코드가 있는 40작업 기준 표준 배치는 validation 76.7%, test 74.9%, randomized 배치는 validation 55.2%, test 52.8%다. 다른 곳의 42작업 집계와 모집단이 다르므로 수치를 섞지 않는다.

실험이 아직 입증하지 않은 것

  • 실로봇 성능: 모든 결과는 시뮬레이션이다. 실제 카메라·메시·물체 크기는 다시 측정하고 파지 폭·운반 속도 등 접촉 변수를 재조정해야 한다.
  • 새 작업의 즉시 실행: 빠른 온라인 실행과 별개로 작업마다 오프라인 개발·시험 비용이 발생한다.
  • 임의 환경의 범용성: Generalization의 표준 layout 77.3%와 randomized 54.1% 사이에 격차가 있다. 전체 70.24%도 완전 성공이 아니다.
  • 코드의 절대적 신뢰성: 명시적 코드라도 부정확한 센서값, 접촉 불확실성, 빠진 복구 분기, hard-coded threshold 때문에 실패한다.
  • 모든 상황에서의 무회귀: fixture 호환성과 기존 작업 재시험은 관측 범위의 보증이다. 통계적으로 큰 회귀를 배제하는 것과 작은 변화까지 없음을 입증하는 것은 다르다.

명시성은 오류를 없애기보다 오류의 위치와 수정 단위를 드러내는 성질로 이해하는 것이 유용하다. 저자들의 “표현이 명확해질수록 상한이 높아진다”는 논의는 연구 방향이며 모든 복잡한 접촉·변형 상태가 이미 충분히 표현된 것은 아니다.

데이터 엔진으로서의 가능성

성공한 작업 프로그램은 여러 배치를 모델 없이 병렬 실행할 수 있고, 궤적마다 명시적 상태와 결정 근거를 남긴다. 이를 VLA 학습 데이터나 Agent Harness의 상태·결정 감독 신호로 사용할 수 있다는 것이 저자들의 제안이다. 이 논문은 그 데이터로 학습한 VLA의 후속 성능 향상을 별도 실험으로 입증한 것은 아니다.

편집 해석 · COAP과 VLA를 경쟁적 대체물로만 볼 필요는 없다. 측정·검증·복구에 강한 코드 계층과 인식·일반화에 강한 학습 계층을 연결할 가능성이 있다. 이는 본 해설의 연구 제안이며 원문 COAP의 시험 설정과 구분한다.

1. Introduction
                                “It is possible to invent a single machine which can be used to compute
                                 any computable sequence.”
                                                                                     Alan Turing [60]

   A Turing machine comprises a tape that stores symbols and a set of fixed rules that read
from and write to the tape [60]. With the rules fixed and only the tape varying, the same rules
can process arbitrary inputs. The same abstraction applies to the physical world, where the
world state is analogous to the tape. A robot reads this tape through perception and writes
to it through action, and its policy plays the role of the rules. We therefore model a robot and
its environment as an Embodied Turing Machine, whose tape holds two kinds of state: the
environment state (e.g., object poses and their spatial relations) and the robot state (e.g., arm
pose and reachable poses).
  Both kinds of state are accurately observable. The robot state is available directly through
proprioception, and object poses can be recovered from RGB images using measured object
geometry. A policy that acts on this state gains two advantages. First, more accurate state
enables more precise action. Second, when objects are rearranged (like different episodes in a
task), only the tape changes, and the same rules (policy) still apply.
   A policy can map state to action in three ways, which differ in how explicit this mapping is.
(i) Vision-language-action models (VLAs). A VLA takes observations, such as camera images,
as input and learns the mapping to action, which remains implicit in its weights [4, 19]. (ii)
Agent harnesses. The vision-language model (VLM) either controls the robot directly, as in
Agent-as-Policy, or directs a VLA, as in Harness VLA [9, 55]. The harness makes part of the
process explicit, such as textual memory, but the VLM and VLA remain black boxes, so we may
still neither fully inspect nor control how an action is derived. (iii) Code-Only-as-Policy (ours).
In contrast, code is a white box that implements the Embodied Turing Machine directly: the
state, such as object poses, is stored in code variables, where it remains accurate, persistent,
and explicit; the rules are written as code logic that computes each action from this state. With
both the state and the rules explicit, no model is required at runtime: the code is frozen and
serves as the sole policy during execution. Code thus becomes a universal interface to the
physical world: a single code program takes over the roles of the VLAs, the prompts and skills
of Agent-as-Policy, and the memory of Harness VLA.

2. Related Work
  Existing robot policies built with foundation models differ in where they keep the state and
how they choose each action from it (Table 1): a VLA encodes the state implicitly in its weights,
and an Agent Harness (Agent-as-Policy or Harness VLA) stores it as text in a model’s context.

Vision-language-action models. RT-2, OpenVLA, 𝜋0 , and 𝜋0.5 learn language-conditioned
visuomotor policies end to end [4, 5, 19, 36], and recent foundation models scale data and
training further [18, 48]. A VLA cannot be inspected or edited directly, so each improvement
requires new data and a new training run, and LIBERO-PRO shows that benchmark success
can reflect memorized training configurations [58]. In comparison, we keep the state in code
variables, so we can backtrack from a failure to the variable that caused it and fix the code
logic that derived it. Each accepted fix is merged into the code without breaking existing logic,
so improvements accumulate, while training a VLA on a new task can degrade its performance
on earlier tasks [61].

VLM (System-2) for robot control. ReAct interleaves reasoning with actions [53], and Tool-
former teaches a model to call tools [38]. In robotics, SayCan grounds language-model plans in
learned affordances [1], and Inner Monologue feeds environment feedback back to the planner
[16]. Recent harnesses let a VLM agent call analytic or learned primitives [9, 55], and GPT-6
Astra [34] has been evaluated directly as an embodied policy [43, 56]. In these systems, the model

even if the prompt is the same. Moreover, every episode is of high cost due to extensive model

cheap because model calls are not required.

Code as an interface for agents. Outside robotics, code has become the medium through

results without regressions on other tasks are merged.

   At step 𝑡 , RoboDojo provides an observation 𝑜𝑡 consisting of an instruction, three RGB images

stage, the arm assigned to each object, retry counts, and the information the task must retain,
such as the color under each cup. It is not part of the tape and plays the role of the internal state
of a Turing machine.

3.3. Sharing one library across tasks that read the same state

  Two design choices make the library reusable across tasks. (i) Every task operates on state
of the same form (§3.1), so a module written for one task can be reused by other tasks. (ii) The
code is layered, with dependencies pointing downward (Figure 3, middle): task programs call
object-specific code, which calls manipulation code such as grasp, pick, place, push, and pour,
which in turn calls perception and motion code. Task code specifies what to do: the order of
subgoals, task-specific decisions, and recovery conditions. The lower layers determine how. For
example, a single transfer call expands into grasp-candidate generation, inverse-kinematics
and collision filtering, a pre-grasp re-measurement, approach, closure, a short lift with a hold
check, carry, placement, release, and a final verification, each of which returns an outcome with
measured evidence. As a result, 83% of the lines are shared across tasks (§4.3.3).
  A new task extends the library in one of three ways (Code Example 2). It can compose existing
modules, such as transfer. It can inherit an existing task and override a single decision: a task
that sorts objects into the baskets named in its instruction reuses the entire flow of an existing
sorting task and replaces only the rule that assigns objects to baskets. Or it can add a default-off
parameter to a shared function: lift_dir allows a grasped object to be lifted diagonally, which
one task requires near a basket wall, while the default preserves the existing vertical lift.

3.4. Improving the code by backtracking failures to the state

  Because the code records its state at every step of an episode, coding agents can improve
the code offline from these records. Improvement proceeds in rounds and is carried out by
Claude Opus 5.5 coding agents, which wrote all code in the library and in every task, ran the
tests and evaluations, and debugged their own code autonomously. Let 𝜃𝑘 be the accepted code
after round 𝑘. Each agent works in its own git worktree, inspects the recorded state of failed
development runs to locate the variable or rule at fault, and proposes a diff Δ. The resulting
branches form a search frontier of runnable code:

                                   C𝑘 = {𝜃𝑘 + Δ𝑘,1 , . . . , 𝜃𝑘 + Δ𝑘,𝑚 }.                           (4)

Because each branch is complete, runnable code, branches can be evaluated concurrently under
identical conditions. Before simulation, each branch passes two CPU checks: the task code is
executed against a numeric scene to confirm that every stage reaches its target state, and the
robot and object meshes are checked for inverse-kinematics solutions and collisions at every
waypoint. Branches that pass are evaluated on the validation episodes (§4.1) in parallel.
   Debugging and selection use separate data. Agents debug on a development set they define
themselves, where they watch videos and compare the measured state against simulator ground
truth; selection compares success counts on the validation split. Let 𝐽𝑞 ( 𝜃; 𝑉𝑞 ) be the success count
of task 𝑞 on these layouts and 𝜖𝑞 a margin above rerun noise. A branch is accepted if

                                  𝐽𝑞 ( 𝜃𝑘 + Δ; 𝑉𝑞 ) ≥ 𝐽𝑞 ( 𝜃𝑘 ; 𝑉𝑞 ) + 𝜖𝑞 ,                         (5)

in which case it becomes 𝜃𝑘+1 and the base of all subsequent branches. Otherwise, the current
code remains deployed and the diff is not merged. The compatibility condition (Equation 3)
protects the tasks that a diff does not target, and the acceptance rule (Equation 5) ensures that the
targeted task improves, so each accepted step is non-decreasing and improvements accumulate.

4.3.2. Execution

 Finding 2. Code-Only-as-Policy controls the state and the decision making. Because the state is
 tracked, failures can be recovered by backtracking and re-attempting through the robust code design.
 Online execution is efficient and cheap since it is model-free.

B1 Controllable. COAP has no model in the online execution, so code controls the state, its
variables, and the decision making. For example, when a bowl held by its rim slipped during
fast carries, one line of code limited the carry speed of rim grasps, and the bowl no longer
dropped. In comparison, a VLA, or a model in the loop of an Agent Harness, is a black box:
some of its uncertainty and errors cannot be fully controlled and accumulate over the execution.
More training trajectories for a VLA, or more text memory for an Agent Harness, still leave its
decisions uncertain.

B2 Recoverable. Because the state is tracked and controlled, the program knows where the
task stands after each step, so it can backtrack and re-attempt. As shown in Figure 6 (middle,
bottom), when an initial grasp fails, the program backtracks, measures the object again, and
re-attempts with a new grasp method, such as a new grasp angle. In episodes where something
went wrong, the program noticed the problem itself in 76% and re-attempted with a new method
in 34% (Figure 6, middle). Recovery matters more as tasks grow longer, since without it one
failed step ends the task (Figure 6, left). In comparison, a VLA has no tracked state to return to.

B3 Efficient. COAP uses a model only offline, when the coding agent writes the code, and the
code is shared by every episode of a task. A control step takes a median of 0.3 ms on a CPU,
and an episode uses 0.8–2.4% of the compute of a VLA and less than 0.1% of that of an Agent
Harness (Figure 6, right). In comparison, an Agent Harness, especially GPT-as-policy, is much
slower and more expensive, and it reasons anew in every episode instead of sharing its decisions
across the episodes of a task.

4.3.3. Extensibility

  Finding 3. Code-Only-as-Policy builds every new task on a shared library by reusing, inheriting, or
  extending its code. Each new task is therefore fast to develop, and capabilities accumulate without
  harming the performance on old tasks.

C1 Reusable. A new task reuses, inherits, or extends the shared library, so its own code holds
only task-specific logic, such as a check or a picking order. As shown in Figure 7 (left), 83%
of the code that new tasks run comes from the library. The library can be shared because its
functions are abstracted step by step at a sensible level (Figure 8). For example, grasping is not
written for each object but by grasp method, such as from the top, by the rim, or by the handle,
so a new object can use an existing method. In comparison, a VLA needs fine-tuning for new
tasks. The memory of an Agent Harness is task-specific and cannot be shared, and its execution
is specific to each episode, so it cannot be shared either.

C2 Fast to evolve.    Since the library is shared, a new task can reuse, inherit, or extend the
existing library, so COAP evolves easily to new tasks. Figure 7 (middle) shows development
on new tasks from scratch, on tasks that had no program when the library was frozen. COAP
reached an average success of 47% within 15 hours, without data or training. Its curve rises
steeply, because the library becomes more robust as it grows, and every task benefits from it.

5. Discussion
  This section discusses what the state of Code-Only-as-Policy (COAP) should contain (§5.1),
where COAP still fails (§5.2), what sets its upper bound (§5.3), its limitations (§5.4), and how it
can serve as a data engine (§5.5).


5.1. What Should the State Contain?

   The state is the tape of the Turing machine (§3), and its five categories are shown in Figure 5
(left). The robot state describes the robot itself: its joint angles, hand poses, gripper openings,
and what each hand holds. The environment state describes the position, size, and class of each
object, the table, and the objects’ spatial relations, such as which object stands on which. The
task state records the task progress, such as the objects picked so far and the current subgoal.
All values are in physical units and are stored in the program.


5.2. Error Analysis of COAP

 Finding 5. COAP still fails in some episodes. The current coding ability has limits, and the offline
 RSI loop needs further optimization so that coding agents write better code. The failures fall into two
 groups: limits of state measurement and limits of the code logic.

 We assigned failed episodes of the runs in Table 2 to the class of the smallest change that
would have prevented them. Figure 11 shows the share of each class and one example of each.

Perception error. The input is RGB only, and recognition is not always accurate, so a wrong
value can enter the state. In Figure 11a, a dartboard in a randomized scene is recognized as the
headset. Such errors may be more severe in real scenes, but better estimation and tools can help.

Contact error.    In principle, the more clearly the state is represented, the higher the upper
bound of the code. For contact, especially with deformable objects, the current representation
of the state is coarse and unclear, so the program cannot always tell how an object is held.
Such contact is inherently hard to represent, but it is still a limit of the state representation. In
Figure 11b, the jaws close on a shirt’s hem, and the soft cloth slips out.

Incomplete logic. The code logic is not robust enough, for example because a retry is missing.
In Figure 11c, the push function stops after one push, although its own check finds a cube still
turned. Within the limited development time, the code was not made fully robust.

5.3. The Upper Bound of COAP

   Finding 6. The upper bound of COAP is set by two factors: how accurately and comprehensively
   the program represents the state, and how robust the code logic is, for example whether it is aware of
   failures and retries.

State representation. Perception and contact errors, 62% of failures, are limits of state measure-
ment (Figure 11, left). Perception errors arise because the input is RGB only, so some estimates
are inaccurate. Contact errors arise because the physical state is hard to represent: for deformable
or otherwise complex objects, part of the contact is not represented well. The more accurately
the state is represented, the higher the upper bound of COAP.

Robust code logic. Incomplete logic and poor code design, 37% of failures, are limits of the
logic (Figure 11, right). More robust code removes them: functions that notice their own failures,
retry with another method, and derive values from the state.


5.4. Limitations

Simulation only. All results are currently in simulation. COAP’s perception relies on the public
configuration and assets of the simulated benchmark, such as the camera parameters, the robot
meshes, and the object sizes, which is a major limitation. On a real robot, these would have to be
measured, and contact-related parameters, such as grip widths and carry speeds, tuned again.

Offline development.      Online execution is fast, but offline development takes time: each
iteration of the code needs evaluation and revision. Unlike a model such as GPT, which can be
used directly as a policy, COAP has a development cost for every new task.

5.5. COAP as an efficient Data Engine for VLAs, Agent-as-Policy and Harness VLA

  Finding 8. COAP produces successful trajectories quickly and reproducibly, so it can serve as a data
  engine for VLAs, Agent-as-Policy, and Harness VLA.

  Once a task program works, it runs on a CPU without a model and can be executed on many
layouts in parallel, so successful trajectories can be obtained very quickly. Each trajectory comes
with the program’s explicit state and the decision behind every action, because the policy is
a white box. These trajectories can train a VLA, and the recorded states and decisions can
supervise the model inside an Agent Harness. COAP can therefore benefit the development of
VLAs and Agent Harnesses.

A new direction. Code-Only-as-Policy differs in many ways from VLAs, World Action Models,
and Agent Harnesses (Agent-as-Policy and Harness VLA, which keep a model in the control
loop): its state is explicit, no model runs during execution, and the policy is improved by coding
agents rather than by training on data. Since its approach differs in so many ways, we view it as
a new direction. If the embodied world is a Turing machine, code can be a universal interface to
the physical world (§1). Our analysis suggests that this direction has advantages (§4.3–§4.4),
and we hope that our exploration can benefit VLAs, Agent-as-Policy, Harness VLA, and RSI.


6. Conclusion
  We propose that the embodied world, a robot together with its environment, is in essence an
Embodied Turing Machine: the world state is its tape, and the robot policy is its rules. On this
basis, we introduce Code-Only-as-Policy (COAP), whose approach differs from those of existing
directions, such as VLAs, World Action Models, and Agent-as-Policy: the state is explicit, the
rules are code, and coding agents improve the code. On RoboDojo, COAP succeeds in 70.24% of
episodes, 38.9% above the state-of-the-art method, and leads all five dimensions. Compared
with a VLA and an Agent Harness, COAP has three advantages (§4.3): Explicit State, Execution,
and Extensibility. Because the policy is a white box, it suits RSI, and its development is efficient
(§4.4). Code still has an upper bound, set by the state representation and the code logic (§5.2–
§5.3), but as coding agents become stronger, this upper bound will rise. We also believe that
COAP can serve as an efficient data engine for VLAs, Agent-as-Policy, and Harness VLA (§5.5).

B. Parallel Branching: Details
Branches and the estimate. A branch is a variant of a program that changes one decision
and is evaluated on the same seeds and layouts as its parent. Figure 10b uses every branch
whose validation success was measured against its immediate parent. Repeated runs of the
same program differ by one to three episodes per evaluation, so the selection margin of four
episodes is one to two noise widths. The estimate of Figure 10c draws 𝑘 effects with replacement
from the measured ones and keeps the best if it reaches the margin, otherwise the parent; the
bands are the 5th and 95th percentiles over bootstrap resamples. The estimate treats branches of
one decision as independent and pools effects across tasks, and each gain is measured on the
layouts that selected it, so the true gain is somewhat lower.
